# Эпик → пул задач → агенты: мануал

Как нарезать эпик на задачи, раздать их агентам (Claude Code и Codex) и довести
эпик до закрытия. Инструменты — скиллы task-flow (проверено по 1.13.0):

- `decompose` — эпик → пул задач с графом зависимостей и волнами;
- `task` — одна задача сквозняком: ingest → spec → premortem ×2 → TDD →
  ревью другой моделью → verify → мерж и закрытие тикета.

Трекер — тот, что записан в биндингах проекта. Основной для линейки — **YouTrack**
(адаптер `decompose` описан на нём, `references/tracker-sync.md` §7); GitHub
Issues — второй вариант, на нём собран демо-стенд `umar-s/tictactoe-lab`. Где
шаги расходятся, ниже две колонки или две подсекции.

## 0. Один раз на проект

Руками это не делается. В корне репозитория запусти `claude` и попроси одной
фразой — для YouTrack:

> «Подготовь репо под task-flow: `AGENTS.md`/`CLAUDE.md` и `.codex/` по
> шаблонам task-flow. Трекер — YouTrack, проект `<KEY>`, MCP-сервер `<имя>`;
> для Codex — тот же MCP в `.codex/config.toml` или REST `<base URL>` с
> токеном в переменной `<ИМЯ>`. Исполнитель задачи — тег `builder:claude` /
> `builder:codex`. VCS — <GitLab|GitHub>, интеграционная ветка `<develop>`,
> MR через `<glab|gh>`, тесты и линт — `<команды>`, мерж — `<self |
> mr-approval-required>`.»

Для GitHub Issues — то же, но «трекер — GitHub Issues этого репо через `gh`,
метки `builder:claude`/`builder:codex`/`epic`, `task-wave.sh` из шаблонов
task-flow — в `scripts/`».

Агент спросит только про внешние шаги. Гейт (`ci/`, protected branch) предложит
поставить `task` в фазе 8, на мерже, если его нет. Что после этого лежит в репо — на
случай, если надо поправить:

- `AGENTS.md` в корне с биндингами: трекер (чтение тикета **с комментариями**,
  комментарий, Done, Spent time, связи parent/depends; токен — по **имени**
  переменной, не значением), интеграционная ветка, как открыть MR/PR и прочитать
  пайплайн, команды тестов и линта, политика мержа. `CLAUDE.md` — первой строкой
  `@AGENTS.md`, ниже только Claude-специфика (имя MCP-сервера трекера для
  ToolSearch); Codex читает только `AGENTS.md`. Скелеты — `templates/agents/` в
  плагине.
- YouTrack в Codex: MCP-сервер в `.codex/config.toml` проекта грузится только
  для trusted project; иначе — REST по базовому URL и имени переменной токена.
  В песочнице `workspace-write` сеть выключена — REST-вызовы трекера из шелла
  идут эскалацией.
- `.codex/agents/reviewer.toml` — ревьюер на случай, когда второй модели нет.
- По желанию `/task-flow:ci-gate` — детерминированный гейт (секреты, миграции,
  unicode). Без него `task` фиксирует `gate: absent` командой и мержит на том
  CI, что есть.

## 1. Эпик → пул задач

```
/task-flow:decompose DEV-480 | "<описание фичи>" | docs/…/spec.md
$task-flow:decompose …                                   # то же в Codex
```

- Выход — `docs/decompose/YYYY-MM-DD-<epic>.md`: требования `REQ-NN`, задачи с
  DoD (включая `truths`), `depends_on`, вычисленная `wave`, трассировка,
  placeholders, открытые вопросы.
- Драфт проверяет независимый субагент в чистом контексте; затем — твоё явное
  одобрение. Для крупного эпика предлагается premortem.
- **Фаза 7 собирает эпик в трекере**: preflight, dry-run всего плана, запись —
  только после твоего «да», затем проверка чтением каждого issue. Ключ
  идемпотентности `decompose-id:<slug>#<n>` лежит в описании — повторный пуш
  обновляет, а не дублирует.

  | | YouTrack | GitHub Issues |
  |---|---|---|
  | эпик ↔ задача | связь `subtask of` | sub-issue |
  | зависимость | связь `depends on` | `blocked_by` |
  | оценка | поле проекта (схема читается, не угадывается) | — |
  | исполнитель | тег `builder:claude` / `builder:codex` | метка `builder:*` |

  Отдельного адаптера GitHub в скилле нет — общий контракт; на стенде это были
  sub-issues и `blocked_by` через `gh`. **Метки и теги `decompose` не пишет**:
  `builder:*` ставишь руками после пуша. Трекер не настроен — стоп на драфте, это
  штатный исход.
- Задача с блокирующим открытым вопросом или `<placeholder: …>` в работу не
  идёт, пока значение не появится.

Одобрение — одной фразой: «Одобряю. Пушь в YouTrack, сначала dry-run.» После
пуша — теги `builder:*` на задачи в YouTrack (или попроси агента отдельным шагом
через тот же MCP: это уже не `decompose`).

## 2. Распределение агентов

Правило: **одна задача = одна сессия = один worktree со своей веткой = один
MR**. Волна — набор задач, которые можно делать параллельно: decompose уже
проверил, что они не пишут одни файлы и общий контракт. Номер волны каждой
задачи — в таблице драфта.

- **Кому что давать.** Поток в обоих харнессах одинаковый; ревью (фаза 6/6b)
  делает другая модель через `xreview.sh --by <другая>`. Тег `builder:*`
  говорит `task`, кто автор, а значит — кто ревьюер.
- **Ширина волны — 2–4 сессии.** `task` идёт под присмотром: вопросы на
  ingest, мерж и внешние шаги подтверждаешь ты. Узкое место — твоё внимание, а
  не слоты.
- **Почему не субагенты из одной сессии.** Субагент не может задать вопрос, а
  `task` спрашивает на ingest и на мерже. Если всё же нужна одна сессия на
  волну — прямо попроси «use a workflow»; разумно доводить задачи до открытого
  MR, а мержить самому.

### YouTrack: волна в tmux вручную

`task-wave.sh` 1.13.0 знает только GitHub Issues (читает готовые задачи и
блокеры через `gh`) — для YouTrack волну поднимаешь сам. Задачи волны берёшь из
таблицы драфта (`wave`), проверив в YouTrack, что их `depends on` в Done.

```bash
cd ~/Project/<repo> && git fetch
tmux new-session -d -s wave-<repo> -n main      # один раз
for id in DEV-481 DEV-482; do                     # задачи текущей волны с тегом builder:claude
  git worktree add "../<repo>-$id" -b "$id" "origin/<develop>"
  tmux new-window -t "wave-<repo>:" -n "$id" -c "../<repo>-$id" "claude '/task-flow:task $id'"
done
# с тегом builder:codex — тот же цикл, но последняя команда окна:  "codex '\$task-flow:task $id'"
tmux attach -t wave-<repo>
```

Перед `worktree add` убедись, что каталога и ветки ещё нет: прерванная задача
продолжается в своём старом worktree (`cd ../<repo>-<ID> && claude` → тот же
`/task-flow:task <ID>` — `task` подхватит `state.md`), а второй агент в одном
checkout'е — гарантированный конфликт. Эти проверки скрипт для GitHub делает сам;
здесь — ты.

### GitHub Issues: волна одной командой — `task-wave.sh` (task-flow ≥ 1.13.0)

Скрипт лежит в плагине: `templates/wave/task-wave.sh`. Один раз скопируй его в
`scripts/` проекта (или попроси агента на шаге 0). Дальше на каждую волну:

```bash
cd ~/Project/<repo>
bash scripts/task-wave.sh --dry-run   # кого запустит: готовые задачи, worktree, команда
bash scripts/task-wave.sh             # запустить волну (или номера: … 12 14)
tmux attach -t wave-<repo>            # войти в сессии
```

Что он делает:

- **Готовые задачи** — открытые issue с меткой `builder:claude` или
  `builder:codex`, у которых все blocked-by закрыты. Эпик (без метки builder)
  не трогается. Номера можно назвать явно.
- **На каждую** — worktree `../<repo>-<N>` на ветке `task-<N>` от свежего
  `origin/main` (`--base develop` — от другой интеграционной ветки) и окно
  tmux `#<N>`, где уже запущен `claude "/task-flow:task #N"` или
  `codex '$task-flow:task #N'` — по метке.
- **Ничего не мержит, не пушит, не удаляет.** Сессии интерактивные: `task`
  спрашивает на ingest и перед мержем.
- **Прервал — запусти снова.** Существующий worktree подхватывается, сессия
  `task` продолжает со своего `state.md`. Повторный запуск безопасен: задача,
  чьё окно `#<N>` ещё живо, второй раз не стартует («already running»), — двух
  агентов в одном checkout не бывает, даже если назвать номер дважды (`2 02`).

Когда он отказывает (rc 2) — до того, как что-то создано:

| Сообщение | Что сделать |
|---|---|
| `not on PATH: codex` (или `claude`, `tmux`) | установить харнесс или перевесить метку `builder:*`; `--dry-run` покажет это заранее |
| `… exists but is not this repository's worktree` / `task-N is checked out at …` | по пути задачи лежит чужой каталог или её ветка занята другим worktree — разобраться руками |
| `another task-wave holds …/task-wave.lock` | уже идёт другой запуск в этом репо; если процесса нет — удалить каталог блокировки |
| `tmux session wave-<repo> belongs to …` | одноимённая сессия чужого репо (тот же basename) — закрыть или переименовать её |
| `cannot read …` / `refusing to guess` | трекер не ответил — это стоп, а не «нет готовых задач» |

Задача с обеими метками `builder:*` пропускается с сообщением — оставь одну.

### Работа в tmux (оба варианта)

| Клавиши | Что |
|---|---|
| `Ctrl-b w` | список окон (задач) — выбрать стрелками |
| `Ctrl-b n` / `Ctrl-b p` | следующее / предыдущее окно |
| `Ctrl-b d` | отцепиться; сессии работают дальше, вернуться — `tmux attach -t wave-<repo>` |

Окно задачи, которой нужен ответ, стоит на вопросе — пробегись по `Ctrl-b w`.

## 3. Порядок волн

- Волна N+1 стартует, когда все её `depends_on` **смержены** в интеграционную
  ветку — открытого MR мало. Worktree — от свежего `origin`.
- Задача упала или закрылась `DONE_WITH_CONCERNS` — зависимые от неё ждут,
  остальные идут.
- Прерванная сессия оставляет `docs/specs/<ID>.state.md`; повторный
  `/task-flow:task <ID>` продолжает с поля `next:`.
- После мержа: `git worktree remove ../<repo>-<ID>`.

## 4. Закрытие эпика

- Каждый `task` в фазе 8 пишет в свой тикет комментарий «что сделано» (первая
  строка — статус). При `DONE` и `DONE_WITH_CONCERNS` — ещё Done и Spent time;
  `BLOCKED`, `MERGED_NOT_LIVE`, `ABANDONED` оставляют тикет открытым.
- Эпик закрываешь ты, когда все дочерние задачи в Done и каждая строка
  `REQ-NN` в трассировке драфта закрыта смерженной задачей.

## Когда нужен другой путь

Повторяющиеся задачи (рутина, а не разовый эпик) — `loop-foundry`: оценка
бэклога YouTrack, триаж, что отдать автономным лупам, лестница shadow → gated →
autonomous.

## Не проверено

- Весь цикл по этому мануалу живьём прогнан только на GitHub Issues
  (`tictactoe-lab`). На YouTrack — нет; в частности `task` в Codex с YouTrack
  (MCP в `.codex/config.toml` или REST) не запускался ни разу.
- tmux-цикл для YouTrack выше — ручные команды, не скрипт: проверены на
  одноразовом репо с заглушкой вместо `claude` (окна в своих worktree, команда
  доходит одним аргументом); проверок `task-wave.sh` (чужой каталог, занятая
  ветка, живое окно) в нём нет.
- `task` без трекера, по provisional ID из драфта: он рассчитан на тикет с
  комментариями, так что для полного цикла нужен настроенный трекер.
