# Эпик → пул задач → агенты: мануал

Как нарезать эпик на задачи, раздать их агентам (Claude Code и Codex) и довести
эпик до закрытия. Инструменты — скиллы task-flow (проверено по 1.13.0):

- `decompose` — эпик → пул задач с графом зависимостей и волнами;
- `task` — одна задача сквозняком: ingest → spec → premortem ×2 → TDD →
  ревью другой моделью → verify → мерж и закрытие тикета.

Волны запускает `templates/wave/task-wave.sh`: по окну tmux с сессией `task`
на каждую готовую задачу. Отвечаешь в окнах и мержишь — ты.

## 0. Один раз на проект

Руками это не делается. В пустом каталоге запусти `claude` и попроси одной
фразой:

> «Подготовь репо под task-flow: каркас на <язык>, CI с тестами,
> `AGENTS.md`/`CLAUDE.md` и `.codex/` по шаблонам task-flow, трекер — GitHub
> Issues, метки `builder:claude`/`builder:codex`/`epic`, `task-wave.sh` из
> шаблонов task-flow — в `scripts/`. Создай приватный репо на GitHub.»

Агент спросит только про внешние шаги (создание репо). Гейт (`ci/`, rulesets)
предложит поставить первая сессия `task`, если его нет. Ниже — что после этого
лежит в репо и зачем, на случай если что-то надо поправить.

- `AGENTS.md` в корне репо с биндингами: трекер (чтение тикета и комментариев,
  комментарий, Done, Spent time, связи parent/depends; токен — по **имени**
  переменной), интеграционная ветка, как открыть PR/MR, команды тестов и линта,
  политика мержа (`self` | `mr-approval-required`). `CLAUDE.md` — строка
  `@AGENTS.md`; Codex читает только `AGENTS.md`. Скелеты — `templates/agents/`
  в плагине.
- Для Codex — `.codex/agents/reviewer.toml`: на нём `task` поднимает свежего
  ревьюера.
- По желанию `/task-flow:ci-gate` — детерминированный гейт (секреты, миграции,
  unicode). Без него `task` фиксирует `gate: absent` командой и мержит на том
  CI, что есть.

## 1. Эпик → пул задач

```
/task-flow:decompose "<описание фичи>" | <EPIC-ID> | docs/…/spec.md
$task-flow:decompose …                                   # то же в Codex
```

- Выход — `docs/decompose/YYYY-MM-DD-<epic>.md`: требования `REQ-NN`, задачи с
  DoD (включая `truths`), `depends_on`, вычисленная `wave`, трассировка,
  placeholders, открытые вопросы.
- Драфт проверяет независимый субагент в чистом контексте; затем — твоё явное
  одобрение. Для крупного эпика предлагается premortem.
- **Фаза 7 собирает эпик в трекере**: сначала dry-run всего плана (задачи,
  связи), запись — только после твоего «да», затем проверка чтением. Задачи
  создаются с `parent` = эпик и связями `depends`. Трекер не настроен — стоп на
  драфте, это штатный исход.
- Задача с блокирующим открытым вопросом или `<placeholder: …>` в работу не
  идёт, пока значение не появится.

## 2. Распределение агентов

Правило: **одна задача = одна сессия = одна ветка в своём worktree = один
PR**. Волна — набор задач, которые можно делать параллельно: decompose уже
проверил, что они не пишут одни файлы и общий контракт.

### Волна одной командой — `task-wave.sh` в tmux (task-flow ≥ 1.13.0)

Скрипт лежит в плагине: `templates/wave/task-wave.sh`. Один раз скопируй его в
`scripts/` проекта (или попроси агента на шаге 0 — «и положи task-wave.sh в
scripts/»). Дальше на каждую волну:

```bash
cd ~/Project/<repo>
bash scripts/task-wave.sh --dry-run   # кого запустит: готовые задачи, worktree, команда
bash scripts/task-wave.sh             # запустить волну (или номера: … 12 14)
tmux attach -t wave-<repo>            # войти в сессии
```

Что он делает:

- **Готовые задачи** — открытые issue с меткой `builder:claude` или
  `builder:codex`, у которых все blocked-by закрыты. Эпик (без метки builder)
  не трогается. Номера можно назвать явно.
- **На каждую** — worktree `../<repo>-<N>` на ветке `task-<N>` от свежего
  `origin/main` (`--base develop` — от другой интеграционной ветки) и окно
  tmux `#<N>`, где уже запущен `claude "/task-flow:task #N"` или
  `codex '$task-flow:task #N'` — по метке.
- **Ничего не мержит, не пушит, не удаляет.** Сессии интерактивные: `task`
  спрашивает на ingest и перед мержем.
- **Прервал — запусти снова.** Существующий worktree подхватывается, сессия
  `task` продолжает со своего `state.md`.
- Ошибка чтения трекера — стоп с rc 2, а не «нет готовых задач».

Работа в tmux:

| Клавиши | Что |
|---|---|
| `Ctrl-b w` | список окон (задач) — выбрать стрелками |
| `Ctrl-b n` / `Ctrl-b p` | следующее / предыдущее окно |
| `Ctrl-b d` | отцепиться; сессии работают дальше, вернуться — `tmux attach -t wave-<repo>` |

Окно задачи, которой нужен ответ, стоит на вопросе — пробегись по `Ctrl-b w`.
Когда все задачи волны смержены, снова `bash scripts/task-wave.sh` —
поднимется следующая волна: её блокеры теперь закрыты.

### Вручную, без скрипта

На каждую задачу текущей волны:

```bash
git fetch && git worktree add ../<repo>-<ID> -b <ID> origin/<integration>
cd ../<repo>-<ID> && claude     # → /task-flow:task <ID>
# или: codex                   # → $task-flow:task <ID>
```

- **Кому что давать.** Поток в обоих харнессах одинаковый; ревью (фаза 6/6b)
  делает другая модель через `xreview.sh`. Задачи можно делить между Claude и
  Codex как угодно — разнообразие ревью от этого не зависит.
- **Ширина волны — 2–4 сессии.** `task` идёт под присмотром: вопросы на
  ingest, мерж и внешние шаги подтверждаешь ты. Узкое место — твоё внимание, а
  не слоты.
- **Почему не субагенты из одной сессии.** Субагент не может задать вопрос, а
  `task` спрашивает на ingest и на мерже. Если всё же нужна одна сессия на
  волну — прямо попроси «use a workflow»; разумно доводить задачи до открытого
  PR, а мержить самому.

## 3. Порядок волн

- Волна N+1 стартует, когда все её `depends_on` **смержены** в интеграционную
  ветку — открытого PR мало. Worktree — от свежего `origin`.
- Задача упала или закрылась `DONE_WITH_CONCERNS` — зависимые от неё ждут,
  остальные идут.
- Прерванная сессия оставляет `docs/specs/<ID>.state.md`; повторный
  `/task-flow:task <ID>` продолжает с поля `next:`.
- После мержа: `git worktree remove ../<repo>-<ID>`.

## 4. Закрытие эпика

- Каждый `task` в фазе 8 сам закрывает свой тикет: комментарий «что сделано»,
  Done, Spent time.
- Эпик закрываешь ты, когда все дочерние задачи в Done и каждая строка
  `REQ-NN` в трассировке драфта закрыта смерженной задачей.

## Когда нужен другой путь

Повторяющиеся задачи (рутина, а не разовый эпик) — `loop-foundry`: оценка
бэклога, триаж, что отдать автономным лупам, лестница shadow → gated →
autonomous.

## Не проверено

`task` без трекера, по provisional ID из драфта: он рассчитан на тикет с
комментариями, так что для полного цикла нужен настроенный трекер.
